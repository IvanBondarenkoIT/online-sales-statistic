# Влияние событий (рекламных кампаний) на продажи — варианты реализации

## Контекст

- **Источник продаж:** Google Таблица «2026 Онлайн продажи» → `data/online_sales.csv` (Date, Sales channel, Product Type, Total Amount).
- **Источник событий:** [Event Calendar](https://docs.google.com/spreadsheets/d/1y_5osZNvVIbvR0d0RubctL5WvlAmZhQ0c4OBzcqsVlo/edit?gid=0#gid=0): рекламные кампании с датами, бюджетом, целевой группой (Sales target = канал, Product Type = тип товара).

**Колонки Event Calendar (по данным таблицы):**

| Колонка | Содержимое | Использование |
|--------|-------------|----------------|
| A | название компании (события) | Отображение в UI |
| B | дата начала | Пересечение с периодом отчёта |
| C | дата конца | Пересечение с периодом отчёта |
| D | бюджет на день | Опционально: ROI |
| E | тип рекламной компании | Контекст |
| G | Sales target | Сопоставление с Sales channel в продажах |
| H | Product Type | Сопоставление с Product Type в продажах |
| I–L, M–P | метрики (клики, затраты и т.д.) | Опционально для расширения |

**Цель:** наглядно показать, как события (рекламные кампании) связаны с продажами: какие кампании шли в выбранном периоде и какие продажи по их целевым группам.

---

## Вариант 1: Блок «События за период» + продажи по целевой группе (рекомендуемый)

**Идея:** На выбранную «На дату» показываем два блока в одном экране:
1. **События, активные в периоде** — список кампаний, у которых [дата начала, дата конца] пересекается с «последние 7 дней» или «последние 4 недели» (на выбор или оба). Для каждого события: название, даты, тип кампании, Sales target, Product Type, при желании бюджет/затраты.
2. **Продажи по целевой группе события** — для каждого события показываем агрегат продаж за период пересечения: только по каналу (Sales target) и типу товара (Product Type) этого события. Так видно: «Кампания X (Facebook, Coffee) → за период кампании продажи Coffee в Facebook = Y ₾».

**Плюсы:**
- Прямая причинно-следственная связь: одно событие → одна целевая группа → одна цифра продаж.
- Минимум изменений в логике: подгрузка событий из отдельного листа (по аналогии с `fetch_sheet`), парсинг дат и целевых полей; фильтрация продаж по Product Type и Sales channel уже есть в отчёте.
- Удобно на мобиле: список событий + под каждым блок «Продажи по целевой группе».

**Минусы:**
- Если у события не заполнены Product Type или Sales target, нужно договориться о правилах (например, показывать все продажи за период пересечения).

**Реализация (очень кратко):**
- Новый источник: `EVENT_CALENDAR_SPREADSHEET_ID` + gid листа, загрузка при «Обновить данные» или отдельным запросом; кэш в памяти или в файле `data/events.csv`.
- Модель события: name, date_start, date_end, sales_target (канал), product_type, опционально budget/cost.
- API: `GET /api/events?date=YYYY-MM-DD` или включить события в ответ `/api/report` (например, `events_in_period`, `sales_by_event`).
- UI: новая секция под сводкой «За 7 дней / За 4 недели» или новая вкладка «События»: список событий за период, под каждым — карточка «Продажи по целевой группе: X ₾, N заказов».

## Вариант 2: Временная шкала (timeline): события поверх графиков

**Идея:** Оставить те же графики «По дням» и «По неделям», но на той же временной оси визуально отметить периоды событий: подписи или цветные полосы «Событие A (3–10 фев)», «Событие B (11–20 фев)». При наведении (или тапе на мобиле) можно показывать тултип: название, целевая группа, продажи по этой группе за отмеченные дни.

**Плюсы:**
- Очень наглядно: «в эти дни шла кампания — вот как вели себя продажи».
- Не нужна отдельная вкладка; всё в контексте уже привычных графиков.

**Минусы:**
- Сложнее UI и логика: нужно рисовать аннотации на Chart.js (плагины или кастомные линии/зоны), аккуратно обрабатывать множество пересекающихся событий и мобильный тап.
- Может быть перегружено, если событий много.

**Реализация (очень кратко):**
- Те же данные событий, что в варианте 1.
- Chart.js: плагин аннотаций (chartjs-plugin-annotation) или ручная отрисовка зон/линий по датам; при клике/тапе — детали события и продажи по целевой группе в модалке или панели снизу.

## Вариант 3: Отдельная вкладка «Аналитика по событиям» (до/после и ROI)

**Идея:** Отдельный сценарий для анализа эффективности: пользователь выбирает период (или «на дату») и видит:
1. Список событий, активных в этом периоде (как в варианте 1).
2. Для каждого события — сравнение «до / во время»: продажи по целевой группе (Product Type + Sales target) за **N дней во время события** и за **такой же N дней до начала события**. Разница и % роста.
3. Опционально: сумма затрат по событию (из колонок затрат таблицы) и простой ROI: (выручка за период события − выручка за период до) / затраты.

**Плюсы:**
- Максимально полезно для решений: «дала ли кампания прирост и насколько».
- Чёткое разделение: основной дашборд — оперативный отчёт; эта вкладка — аналитика по кампаниям.

**Минусы:**
- Больше логики (два периода, нормализация по длине события, парсинг затрат из таблицы).
- Затраты в таблице могут быть в разных колонках (I–L и M–P) и форматах — нужна договорённость по структуре.

**Реализация (очень кратко):**
- Общая загрузка событий + маппинг колонок затрат (например «Сумма затрат»).
- API: например `GET /api/events-analysis?date=YYYY-MM-DD` возвращает для каждого события: period_during, period_before, revenue_during, revenue_before, change_pct, optional cost, optional roi.
- UI: вкладка «Аналитика по событиям» с карточками: событие, даты, «Во время: X ₾», «До: Y ₾», «+Z%», при наличии — «Затраты / ROI».

## Сравнение и рекомендация

| Критерий | Вариант 1 | Вариант 2 | Вариант 3 |
|----------|-----------|-----------|-----------|
| Наглядность связи событие → продажи | Высокая | Очень высокая | Высокая (акцент на прирост) |
| Сложность реализации | Низкая | Средняя/высокая | Средняя |
| Риск перегруза UI | Низкий | Средний | Низкий |
| Полезность для «вижу ли влияние» | Высокая | Высокая | Очень высокая |
| Зависимость от формата затрат в таблице | Нет | Нет | Да (для ROI) |

**Рекомендация:** начать с **Варианта 1** (блок «События за период» + продажи по целевой группе): быстрее внедрить, понятная связь «событие → целевая группа → продажи», без изменения существующих графиков. При необходимости позже добавить Вариант 2 (аннотации на графиках) или Вариант 3 (вкладка до/после и ROI) поверх того же слоя данных событий.

## Технические общие шаги (для любого варианта)

1. **Конфиг:** в `config.py` (или отдельный модуль) добавить `EVENT_CALENDAR_SPREADSHEET_ID`, `EVENT_CALENDAR_SHEET_GID` (для листа Event Calendar).
2. **Загрузка событий:** скрипт или функция по аналогии с `fetch_sheet`: CSV export по gid, парсинг дат (дата начала/конца в форматах таблицы), нормализация названий колонок (Sales target, Product Type). Сохранение в `data/events.csv` или отдача из API без кэша на диске.
3. **Сопоставление с продажами:** по периоду (пересечение [ref−6, ref] или 4 недель с [date_start, date_end]) и по полям Sales channel ↔ Sales target, Product Type ↔ Product Type. Учесть пустые/разные написания (нормализация регистра и пробелов).
4. **API:** один или несколько эндпоинтов, возвращающих события за период и (при необходимости) агрегаты продаж по каждому событию; фронт только отображает готовые данные.

После выбора варианта можно расписать по шагам конкретные изменения в `config`, загрузчике, `app.py`, `report_data` (или новом модуле) и в `static/index.html`.
